# 07. MCP server

Revision 0.1 of 30.09.2026, written against the code of task T22 (editor 1.2). The design with its alternatives and the
reasons for every decision is [todo/T22-mcp-server.md](todo/T22-mcp-server.md); where that design and the code differ,
the code is right and this document follows the code. The user page is `docs/user/<lang>/mcp.md`
([English](../../user/en/mcp.md)).

## 1. Purpose and boundaries

- An MCP server (Model Context Protocol, revision 2025-06-18, JSON-RPC 2.0) inside WinKickOff with two transports:
  stdio (an AI client starts a headless process) and Streamable HTTP on `127.0.0.1` (started and stopped from the
  running window; also headless for tests and a virtual machine). Clients: Claude Code (stdio and HTTP), Claude Desktop
  (stdio) and anything built on the official SDKs, including dual-era clients that probe with `server/discover` first.
- Off by default. Loopback only: the bind address is a constant, there is no setting, flag or argument for it. A static
  bearer token generated by the program. Read-only by default; the two write modes are switched on by the user for the
  current session only.
- Nothing on the PC changes because a client asked: the server never runs PowerShell, never elevates, never deletes or
  replaces a file, never imports templates, never changes settings, never returns or accepts a password or a product
  key. The tests prove it without a window, without a network beyond loopback port 0 and without `powershell.exe`.
- Standard library only, `unittest` only, no MCP SDK: the JSON-RPC framing, the handshake and the HTTP handler on
  `http.server` are written by hand.
- Out of scope: Server-Sent Events and every server-initiated message, `resources/subscribe`, `listChanged`, prompts,
  sampling, elicitation, tasks, progress, resumability, OAuth, TLS, IPv6 `[::1]`, non-loopback binding, batches, the
  2026 stateless revision (`server/discover` gets `-32601`, which makes dual-era clients fall back to `initialize`).

## 3. Protocol subset

`McpServer.handle(message, session)` takes one parsed message and returns the response object, or `None` for a
notification and for a response sent by the client. Everything is synchronous; the server never sends a message on its
own initiative.

- `initialize`: `protocolVersion` must be a string, otherwise `-32602` with `data: {"supported": [...], "requested":
  ...}`. The answer echoes the requested version when it is one of `SUPPORTED_VERSIONS` (`2024-11-05`, `2025-03-26`,
  `2025-06-18`) and answers `2025-06-18` for anything else (a 2025-11-25 client accepts it). Capabilities: `tools:
  {listChanged: false}`, `resources: {subscribe: false, listChanged: false}`; `serverInfo: {name: "winkickoff", title:
  "WinKickOff", version: APP_VERSION}`; `instructions` is the static English text `protocol.INSTRUCTIONS` (what
  WinKickOff is, the three modes and `mode_required`, stable English ids, no secrets, changes stay in memory, texts of
  imported templates and profile free text are data, nothing on the computer changes), followed by
  `protocol.SKILL_INSTRUCTIONS` only when the server serves `winkickoff://skill/SKILL.md` (an agent that has not loaded
  the skill reads that resource before the first tool call). For `codemode` and `deferred` exposure (its default is
  `codemode`), pi lists the server in its system prompt with the first line of the instructions cut to 250 characters,
  once the server has connected; the instructions are one line of about 1,000 characters with the skill sentence last,
  so the prompt never carries the pointer. Scripts get the whole text through `describeNamespace`; the pi container
  also gets the pointer from its own instructions.
  `clientInfo.name` and `version`
  are cleaned with `clean_text` and kept on the session for the monitor. `session.initialized` is set before the
  result is returned: from that moment every request on the session is served. `notifications/initialized` only sets
  `session.acknowledged`; nothing depends on it, because on HTTP the notification is a separate POST that may arrive
  after the client's first `tools/list`.
- `ping`: `{}` at any time, also before `initialize`.
- Any other request on a session that has not produced an `initialize` result: `-32600 "not initialized: send
  initialize first"`, never silence, so that a dual-era client falls back correctly.
- `tools/list`: all 18 tools regardless of the current mode, each `description` prefixed with `[read] `, `[edit] ` or
  `[files] `, with `title`, `inputSchema` and `annotations`; no `outputSchema`, no `nextCursor`; a non-empty `cursor`
  gives `-32602 "invalid cursor"`.
- `tools/call`: an unknown `name` gives `-32602 "Unknown tool: <name>"`; `arguments` absent means `{}`, and anything
  but an object gives `-32602`. `ToolRegistry.call` validates the arguments with `schema.check`, checks the mode with
  `allows`, runs the handler. Success: `{"content": [{"type": "text", "text": <compact JSON>}], "structuredContent":
  <object>, "isError": false}`; `preview_build` puts the previewed text itself into the text block. A `ToolError`
  becomes `{"content": [{"type": "text", "text": message}], "structuredContent": {"error": kind, "message": message,
  ...data}, "isError": true}`.
- `resources/list`, `resources/templates/list`, `resources/read` (section 10). Anything not addressable gives `-32002`
  with `data: {"uri": ...}`.
- Notifications `notifications/initialized`, `notifications/cancelled`, `notifications/progress` and
  `notifications/roots/list_changed` are accepted; any other notification is logged at DEBUG and ignored. Every other
  request (`server/discover`, `logging/setLevel`, `prompts/list`, `completion/complete`, `resources/subscribe`, ...)
  gets `-32601`.
- Batches (JSON arrays) are refused by `parse_message` with `-32600 "batches are not supported"`; on stdio that is the
  answer line, on HTTP a `400` with that body.
- Any other exception inside a handler becomes `-32603 "internal error"` without a traceback; the logger
  `winkickoff.mcp` gets `"<tool or method>: <ExceptionClass>"` at ERROR and the traceback at DEBUG only, so no
  argument text reaches a log file at the default level.
- Result size: a serialised result above `MAX_RESULT_BYTES` is replaced by the tool error `result_too_large` (with
  `bytes`) or, for a resource, by a `-32603` with the same message: "narrow the query (group, query, limit, offset)".
- Concurrency: `tools/call` and `resources/read` run under one lock (`_call_lock`); `ping`, `initialize` and the lists
  do not take it.
- Every answer is JSON. No SSE stream is ever opened (GET is `405`), so the client never has to hold a connection.

## 4. HTTP transport

Bind: `McpHttpServer(port, token, server)` calls `ThreadingHTTPServer.__init__((HOST, port), McpHandler)` with `HOST =
"127.0.0.1"`; port `0` takes any free port, and the bound port is read back through `httpd.port`
(`server_address[1]`). `allow_reuse_address = False`; on win32 `server_bind` sets `SO_EXCLUSIVEADDRUSE` before binding,
so another process of the same user cannot take the port with `SO_REUSEADDR` and receive the connections (and the
bearer token) meant for this server. A second listener on the same port gets `OSError`, which the window reports as
"port N is used by another program". `daemon_threads = True`, `block_on_close = False`, `request_queue_size = 8`.

Handler: `McpHandler(BaseHTTPRequestHandler)` with `protocol_version = "HTTP/1.1"`, `server_version = "WinKickOff"`,
`sys_version = ""` (no Python version reaches an unauthenticated caller), socket `timeout = 30`. Every response carries
an exact `Content-Length`, `Cache-Control: no-store` and `Connection: close`, and `close_connection` is set, so a
handler thread lives for one request and `shutdown()` returns within the poll interval. `log_message` and `log_error`
write the request line at DEBUG on `winkickoff.mcp.http`.

Checks, in order; a failing check ends the request with a minimal response and no JSON-RPC processing, so banner
grabbing gets nothing before authentication:

| Step | Check | On failure |
|---|---|---|
| 1 | `Host` equals `127.0.0.1:<port>` or `localhost:<port>` (host part case-insensitive) | `421`, empty body |
| 2 | `Origin`, when present, equals `http://127.0.0.1:<port>` or `http://localhost:<port>`; `null` is refused | `403`, empty body; no CORS headers, ever |
| 3 | `Authorization: Bearer <token>`, compared with `hmac.compare_digest`; the token is never accepted in a query string | `401`, empty body, no `WWW-Authenticate` (a challenge would send SDK clients into an OAuth discovery that cannot succeed) |
| 4 | The path is exactly `/mcp` | `404`, empty body (also for `/.well-known/*`, so that discovery fails fast) |
| 5 | `MCP-Protocol-Version` is absent or one of `HEADER_VERSIONS` (the supported versions plus `2025-11-25`) | `400` |
| 6 | Method: `POST` continues; `DELETE` ends the session named by `Mcp-Session-Id`; `GET`, `HEAD`, `OPTIONS`, `PUT` and `PATCH` are refused | `DELETE`: `204` or `404`; the others `405` with `Allow: POST, DELETE` |
| 7 | A slot of the `BoundedSemaphore(MAX_CONCURRENT)` is free | `503` with `Retry-After: 1` |
| 8 | No `Transfer-Encoding`; `Content-Length` present and made of digits only (no sign, no spaces) | `411`; anything else `400` |
| 9 | `Content-Length` at most `MAX_MESSAGE_BYTES`; a larger body is first drained (up to `DRAIN_LIMIT` in 64 KB chunks; a request that failed one of the checks above drains at most 64 KB), so the client sees the status instead of a reset | `413` |
| 10 | `Content-Type` starts with `application/json` | `415` |
| 11 | `Accept` absent, `*/*` or containing `application/json` | `406` |
| 12 | The body parses with `parse_message` | `400` with a JSON-RPC body: `-32600` for an array, `-32700` for bad JSON (`id: null`) |
| 13 | Session: an `initialize` request creates one and returns its id in `Mcp-Session-Id`; a `ping` without a session id is served on a throw-away session; every other message needs the header | missing: `400` with a `-32600` body "Mcp-Session-Id header required"; unknown: `404`, empty body |
| 14 | Dispatch through `McpServer.handle` | a notification or a client response: `202`, empty body; a request: `200`, `application/json; charset=utf-8`, the JSON-RPC response (also for a `-32603`) |

Sessions: `Session(secrets.token_urlsafe(24), "http")` kept in `httpd.sessions` under a lock; at most `MAX_SESSIONS`
(16), the oldest by `last_seen` is evicted. There is no idle expiry: a session ends on `DELETE`, by eviction or when the
server stops; a restarted server has an empty dictionary, so a client that outlived the restart gets `404` and
re-initializes, as the specification requires (the SDK clients do it on their own; a hand-written client must be told,
and the user page says so). Sessions are not authentication (the token is): they exist to know the client name for the
monitor and to give a restarted server a clean `404`.

Threads and stop: the serving thread `threading.Thread(target=serve, args=(httpd,), name="mcp-http", daemon=True)`
runs `serve(httpd)`, which sets `httpd.serving` and calls `serve_forever(poll_interval=0.5)`. `McpService.stop()`
takes the server and the thread under its lock, calls `httpd.shutdown()` only when the thread is alive and
`httpd.serving` is set (otherwise `BaseServer.shutdown()` would wait forever on an event that only `serve_forever`
sets), then `server_close()`, `thread.join(join_timeout)` and `bridge.fail_all(RuntimeError("server stopped"))`.
`Connection: close` and `block_on_close = False` make this return at once even with a client connected.

Why JSON only: the 2025-03-26 and 2025-06-18 texts allow a server to answer every POST with `application/json` and to
refuse GET with `405`; the TypeScript client treats the `405` as "no stream". Without SSE there are no idle handler
threads, no resumability and nothing to clean up on stop.

Windows Firewall: a listener bound to `127.0.0.1` creates no rule and no prompt, because loopback traffic is not
filtered; this is confirmed in CI and in the VM acceptance before HTTP tests run on the customer's PC.

## 5. stdio transport

`serve_stdio(reader, writer, server, session)` runs in the main thread of the headless process (Windows has no `select`
on pipes; blocking reads are the only portable choice):

- `reader.readline(MAX_MESSAGE_BYTES + 1)`. A chunk that does not end with a newline and is longer than
  `MAX_MESSAGE_BYTES` is an over-long line: the loop drains the rest of the line (chunks discarded until one ends with a
  newline or EOF), answers one `-32700` with `id: null` and continues; the tail of an over-long line is never parsed as
  a message. Invalid UTF-8 or JSON is answered with `-32700` (`id: null`) and the loop continues. Blank lines are
  skipped. EOF ends the loop; `BrokenPipeError` and `KeyboardInterrupt` end it as well; the function returns 0.
- Every answer is `dumps(obj) + b"\n"` followed by `flush()`; `dumps` asserts that the text holds no raw newline
  (`json.dumps` without `indent` never emits one; U+2028 and U+2029 are not newlines for `readline`). Nothing else is
  ever written to stdout: logging goes to a file (section 14), and `print` exists only in `cli.py` for usage,
  `--version` and `--mcp-config`.
- One `Session("stdio", "stdio")`; `initialize` is still required before other requests.
- `open_std_streams()` returns `sys.stdin.buffer` and `sys.stdout.buffer` when Python made stream objects, otherwise
  `os.fdopen(0, "rb", buffering=0)` and `os.fdopen(1, "wb", buffering=0)` when `os.fstat` succeeds on both descriptors
  (a `--noconsole` process whose parent passed pipes), otherwise `None`; the caller then logs "no standard streams" and
  exits 3.
- Termination: the client closes stdin, then terminates the process; nothing runs in other threads, so nothing needs
  cleanup.

## 6. Token and settings ownership

Settings fields (`core/settings.py`, validated in `load` and written by `save` like every other field):

| Field | Type, default | Validation |
|---|---|---|
| `mcp_port` | `int`, `47831` | `valid_port`: `0` or `1024` to `65535`, never a boolean; otherwise the default |
| `mcp_token` | `str`, `""` | `TOKEN_RE = ^[A-Za-z0-9_-]{32,64}$`; otherwise `""` |
| `mcp_autostart` | `bool`, `False` | `is True` |

Not stored: the mode (every start is `read`, autostart included), the running state, the bound port, the sessions, the
journal. `allow_apply` is orthogonal: the MCP layer never reads it and never reaches the apply code.

The window's `Settings` object is the only writer of `settings.json`. `create_app` loads the settings, calls
`service.configure(paths, settings)` before the window exists, builds the window on the same object and then sets
`service.on_save = root.save_settings`; after a window rebuild (language, theme, templates) `create_app` runs again
with the freshly loaded settings, which already hold the token the previous window saved. `McpService.ensure_token()`
runs on the main thread (from `start_http`, `copy_mcp_token` and `copy_mcp_config("http")`): when the stored token does
not match `TOKEN_RE` it stores `secrets.token_urlsafe(32)` (43 characters) on the settings object and calls `on_save`.
`rotate_token()` stops a running server, stores a new value and saves; the window asks first, because clients with the
old token stop working. A headless process calls `configure(paths, settings)` without a callback and never calls
`Settings.save`: `--mcp http` takes the token from `--token` or from `settings.mcp_token` and exits 2 when both are
empty; `--mcp stdio` needs no token.

The token is compared with `hmac.compare_digest`, never logged, never drawn in clear text (the monitor shows
`masked()`, `abcd...wxyz`) and reaches the clipboard only through "Copy token" and "Copy client configuration (HTTP)".
It lives in `settings.json` next to `profiles/*.json`, which already hold passwords in plain text, so a reader of the
program folder gains nothing new, and the token only works from the same computer.

## 7. Modes and the never-available list

`McpService.mode` is one value read at every `tools/call` through `ToolContext.mode`, so a change in the window applies
to the next call. Each `ToolSpec` declares the minimum mode it needs; `allows(current, required)` compares positions in
`MODES`. A refused call is the tool error `mode_required` with `required`, `current` and `how` ("the user switches the
mode in the MCP menu of the WinKickOff window, or starts the server with --mode").

| Mode | Tools | Effect |
|---|---|---|
| `read` (default at every start) | `get_status`, `list_groups`, `list_rules`, `get_rule`, `get_profile`, `list_profiles`, `diff_profile`, `check_profile`, `preview_build`, `get_messages`, every resource | Nothing changes, not even the selection |
| `edit` | plus `set_rules`, `set_group`, `set_param`, `set_profile_info`, `load_profile`, `show_item` | The profile in memory; the window shows unsaved changes |
| `files` | plus `save_profile`, `write_answer_file` | New files inside `profiles/` and `output/`; existing files are never replaced |

How the mode is chosen: three radio items of the `MCP` menu (`change_mcp_mode`) and the same combo box in the monitor;
`files` asks once per window (`_files_confirmed`) with a warning box defaulting to "No"; the command line `--mode` for
headless processes; the stdio snippet of `client_config` writes `--mode edit` when the window is in `edit` or `files`
and never writes `--mode files`. The mode is never persisted.

Never available, in any mode. The registry has no handler for these, no tool schema has a property whose name contains
`path`, and the tests call every tool and resource in `files` mode with the forbidden functions patched to fail:

- `apply.launch_elevated`, `apply.run_audit`, `MainWindow.apply_now`, `revert_now`, `audit_selected`: a UAC prompt
  triggered by an agent, or generated code run on the PC.
- `pscheck.check_scripts`: it spawns `powershell.exe`. `write_answer_file` therefore writes without the PowerShell
  syntax check and says so (`powershell_checked: false` and an `info` issue).
- `admx.save_import`, `admx.read_templates` on a caller-given folder, `admx.rename_import`, `admx.delete_import`,
  `MainWindow.import_templates`.
- Any deletion, overwrite or rename of a file, anywhere.
- `Settings` reads or writes through the protocol: `allow_apply`, language, theme, recent files, the port, the token,
  the mode, autostart.
- Passwords and product keys in either direction; the accounts, languages and installation data forms.
- Raw contents of `profiles/*.json`, `output/*.xml`, `logs/*`, `settings.json`, `admx/**`.
- File system paths as arguments: every file argument is a name checked by `check_name` and resolved by `safe_child`
  inside one fixed folder.
- Server control from inside the protocol (stop, restart, mode, token), window rebuilds (`change_language`,
  `change_theme`, `show_templates`), `os.startfile` and folder opening.

## 8. Workspace, bridge and window

Rule: no tkinter call, no `Profile` access and no `Catalog` construction from a server thread. A `Catalog` is immutable
after `with_imports` and may be read from any thread; a `Profile` is touched only on the thread that owns it.

The `Workspace` protocol (`mcp/workspace.py`): `snapshot() -> Snapshot`, `set_rules(items) -> (changes, refused)`,
`set_group(group_id, action) -> changes`, `set_param(rule_id, name, value) -> stored value`, `set_profile_info(name,
author, comment)`, `load_profile(path, force) -> warnings`, `show_item(item) -> bool`, `save_profile_to(path)`,
`write_answer_file_to(path) -> (BuildResult, issues)`, `current_issues()`, `is_busy()`. `Snapshot` is a frozen
dataclass with the shared `catalog`, a `profile` copy, `resources`, `paths`, `dirty`, `profile_file` (display path),
`selected` (the tree item shown), `issues` and `language`.

Shared logic, used by both implementations so that an agent can do nothing a click could not:

- `apply_rule_states(catalog, profile, resolver, items)`: for every `(id, enabled)` the `Resolver.set_rule` cascade;
  an imported policy that follows a built-in rule (`linked.link`) switches that rule instead when the values are equal,
  is refused with the text of the window's own question when the built-in rule also sets other values, and is skipped
  when it is already on through that rule; then `drop_redundant` switches off imported policies an enabled built-in
  rule now writes anyway. Returns the changes and the refused ids with reasons.
- `apply_group_action(catalog, profile, resolver, group_id, action)`: `on`, `off` (`Resolver.set_group`) or `defaults`
  (`Resolver.reset_group`), plus `drop_redundant`; an imported group can only be switched off (`refused`).
- `change_param(catalog, profile, resources, rule_id, name, value)`: `normalise_param_value` (the parameter type; a
  boolean is never an enum value, since `True == 1` in Python, and 1.3 refuses it), `validate.check_param` (the same
  check as the parameter panel), then the value is stored (removed when it equals the default) and rejected with
  `validation_failed` when `validate_profile` reports an error that was not there before; the previous parameters are
  restored.
- `check_and_build(catalog, profile, resources, templates, app_version)`: `validate_profile`, `Renderer.build`,
  `validate_xml`; the window's Check without PowerShell.
- `profile_file(paths, name)`: the preset ids `office`, `strict`, `laptop`, `home` resolve to `paths.data /
  "profiles" / "preset-<id>.json"`, everything else to `safe_child(paths.profiles, name, ".json")`.
  `list_profile_files(paths)` scans `paths.data / "profiles"` for `preset-*.json` and `paths.profiles` for user files
  (the two folders differ in the frozen build and coincide only when running from sources) and counts files whose stem
  fails `check_name` as `unlisted`.

`HeadlessWorkspace(paths, catalog, profile, resources, app_version)` implements the protocol on a profile in memory:
`show_item` returns `False`, `is_busy` returns `False`, `load_profile` refuses with `unsaved_changes` when dirty and
`force` is false, `write_answer_file_to` raises `validation_failed` on errors and appends the `info` issue
`POWERSHELL_NOTE` ("PowerShell syntax not checked: build the file in the window (F9) to check it"; the window's Check, F7, does not run the PowerShell check either).

`WindowWorkspace(window)` (`ui/mcp_workspace.py`) implements it on `MainWindow` through the dialog-free methods the
window's own handlers also use: `apply_rule_states` (one `_apply_changes` and one `show_item` for the whole list),
`apply_group_action`, `set_param_value` (marks dirty, refreshes marks, updates the status bar and the open card),
`set_profile_info` (dirty, title, status), `load_profile_file(path, confirm=False)` (no "Save changes?" question and
no error box; the workspace refuses with `unsaved_changes` first), `select_node`, `save_profile_to` (the tail of Save
as: name, save, recent list, title), `write_answer_file_to` (`run_checks(with_powershell=False)`, `write_build`, the
`info` issue), `current_item`, `current_issues`, `is_busy`. Every method runs on the tkinter main thread.

The bridge (`mcp/bridge.py`) is the single crossing point:

- `Bridge.run(fn, writes, timeout)` from a server thread: refused with `window_timeout` ("the editor window is not
  available (restarting or closed)") when no workspace is attached; otherwise an `Item(fn, writes, deadline)` with a
  `Future` goes on the queue and the caller waits `future.result(timeout)`. Reads use `BRIDGE_TIMEOUT` (5 s), writes
  `WRITE_TIMEOUT` (30 s). On timeout, under the item lock: a still queued item is marked `abandoned` and `window_timeout`
  is raised ("busy, a dialog is open, or it is restarting"); an item that already started cannot be undone, so `run`
  waits `BRIDGE_TIMEOUT` more and returns the result when it arrives; if even that expires, the item is remembered as
  late and `window_timeout` is raised with "the change may still land, check with get_profile" and `data: {"pending":
  token}`.
- `Bridge.pump(max_items=20, budget=0.05)` on the owning thread: skips items that are no longer queued, fails items
  whose deadline passed (`window_timeout`, "the request expired before the window ran it"), fails write items with
  `window_busy` while `workspace.is_busy()` (reads go on), marks the rest `running`, calls the closure and settles the
  future. A closure that started completes, and its change is visible in the window as an unsaved change. When the
  caller had given up, the late callback fires with "completed after timeout".
- `McpServer._note_late` registers that callback through `bridge.note_late(token, ...)` so that the journal entry of
  the timed-out call is annotated "completed after timeout"; the monitor shows it in the result column.
- `fail_all(exc)` fails every queued item (the server stops). `InlineBridge` (headless and tests) runs the closure
  directly on the calling thread under an `RLock`.

Every read tool starts with `ctx.snapshot()`, which runs `ws.snapshot()` on the main thread and returns the catalog
reference and `profile.copy()`; the heavy work (`Renderer.build`, `validate_profile`, `validate_xml`, action
rendering) then runs on the server thread against the copy. A write tool submits one closure that performs the whole
change on the main thread and returns its result: one tree refresh per call, not per rule.

Busy and modal states in the window: every message box and file dialog goes through `MainWindow._dialog(show, *args,
**kwargs)`, which increments `self._modal` around the call (`tests/test_sources.py` keeps it so for every future
dialog in `ui/`). `is_busy()` returns `self._busy or self._modal > 0 or self.grab_current() is not None`: native Windows
dialogs (`MessageBoxW`, the common file dialogs) set no Tk grab, so the counter is what catches "Save changes?" and the
save dialog after a build; the grab covers Tk-drawn dialogs. `after` timers keep ticking under the nested message loop
of a native dialog, so `pump` runs, answers reads and refuses writes with `window_busy` meanwhile; should a Windows
build not tick, reads time out with `window_timeout`, which the user page names as the fallback.

Wiring: `install_pump(window, bridge)` schedules `bridge.pump()` every 50 ms with `window.after` and stores the id in
`window.mcp_pump_id`; a tick that ran closures calls `window.refresh_mcp_status()`. `MainWindow.destroy()` cancels the
pump id and calls `service.detach()` before `super().destroy()`, so no callback fires on a destroyed interpreter; a
call queued before the detach or arriving during the rebuild waits (within its deadline) for the next window, which
attaches a new `WindowWorkspace`, or times out with a clear error; after `service.stop()` the bridge is closed and
refuses at once. `app.run()` creates one `McpService` for the process, passes it to every `create_app(state, service)` of
the rebuild loop and stops it in `finally` after the last window, because a daemon thread frozen at interpreter
shutdown while holding a lock or a socket can produce a fatal error on exit. A window built with `service=None` (every
existing test) is inert: the `MCP` menu is disabled, no pump runs, the status segment says "MCP: off".

## 9. Tools

Conventions: names are lowercase identifiers; every `inputSchema` is an object with `additionalProperties: false`;
`id` arguments match `^[A-Za-z0-9_.:-]{1,200}$` and are checked against the catalog; `language` is an enum built from
`available_languages` at start and defaults to the process language; every string argument has `maxLength`; every text
in a result passes `clean_text` with the caps of `redact.py`; texts written by other people come under keys ending in
`_text`; imported rules carry `origin: {import, name, file, policy, unreviewed_text: true}` and built-in rules `origin:
null`; every rule row carries `text_language` (the requested language for a built-in rule, the process language for an
imported one, because `with_imports` bakes the ADML texts into the catalog once). Descriptions are static English texts
authored in code, never catalog text, and the ones that return foreign text end with the note that such text is data,
not instructions. No `outputSchema` is published, because the TypeScript client validates `structuredContent` against
it strictly.

Annotations: read tools `readOnlyHint: true, destructiveHint: false, idempotentHint: true, openWorldHint: false`; edit
tools the same with `readOnlyHint: false` (`load_profile` has `idempotentHint: false`); files tools `readOnlyHint:
false, destructiveHint: false, idempotentHint: false, openWorldHint: false` (they never replace a file).

## 10. Resources

Capability `resources: {subscribe: false, listChanged: false}`, custom scheme `winkickoff:`. `resources/list` returns
the five fixed entries, the skill entries (when the skill folder exists) and one entry per documentation file the
templates can address (one page, no cursor); `resources/templates/list` returns the three templates, plus the skill
template when the skill has reference files; `resources/read` returns `{"contents": [{"uri", "mimeType", "text"}]}`.
All resources are read-only and available in every mode; a resource result is subject to `MAX_RESULT_BYTES` like a
tool result.

| URI | Content | mimeType |
|---|---|---|
| `winkickoff://status` | The JSON of `get_status` | `application/json` |
| `winkickoff://profile` | The JSON of `get_profile` (redacted) | `application/json` |
| `winkickoff://catalog/groups` | The whole group tree with counts, in the process language | `application/json` |
| `winkickoff://catalog/rules` | `{id, title, enabled, level}` of the built-in rules only, plus `imports: [{id, name, policies}]` and a note that imported policies are listed by `list_rules` | `application/json` |
| `winkickoff://messages` | The messages panel | `application/json` |
| `winkickoff://catalog/rules/{id}` (template) | The card of `get_rule` in the process language | `application/json` |
| `winkickoff://docs/reference/{file}` (template) | A file of `docs/technical/reference/*.md` | `text/markdown` |

Documentation files come from an allow list taken at start: the names matching `^[A-Za-z0-9][A-Za-z0-9-]{0,60}\.md$`
in `docs/technical/reference` and in `docs/user/<lang>` under `paths.docs_root`. A read resolves the path, requires
`resolved.is_relative_to(docs_root / "docs")` and a regular file, cuts the bytes at `MAX_DOC_BYTES` (64 KB) and passes
the text through `clean_text`. URI parsing is a split on `://` and `/`; the appendices, the technical editor
documentation, `AGENTS.md`, `settings.json` and `logs/` are not addressable. An unknown scheme or path, a name outside
the allow list, a missing file or a `ToolError` raised underneath gives `-32002` with `data: {"uri": ...}`.

skill installer) follow the skill. The folder is `paths.root / "skills" / "winkickoff"`: `WinKickOff/skills/winkickoff` from
sources, `skills\winkickoff` next to `WinKickOff.exe` in the portable build (`tools/build.ps1` copies it). The allow
list is taken at start like the documentation: `SKILL.md` when it is a regular file, and the names of `references/`
matching the same pattern (no subfolders, no other extensions). A read requires `resolved.is_relative_to(skill folder)`
and a regular file, cuts at `MAX_DOC_BYTES` and applies `clean_text`; an `OSError` while reading is a `-32002` too.

normally. `tests/test_skill.py` checks that every skill file is served whole (each is under `MAX_DOC_BYTES`), and that
every file fits the 20 KB pi 0.99.2 shows of a direct MCP text (it cuts the middle of anything longer); a pi
`codemode` script gets a result whole.

## 11. Redaction

Always on; no tool or resource returns a password or a product key.

- `clean_text(text, limit)`: removes C0 and C1 control characters except newline and tab (CR LF and CR become LF),
  the zero-width and bidi formatting characters (U+200B to U+200F, U+202A to U+202E, U+2060 to U+2064, U+2066 to U+2069)
  and U+FEFF, then truncates at `limit` with the suffix ` [truncated]`. Caps: `TITLE = 200`, `SUMMARY = 400`,
  `EFFECT = 2000`, `EXPLAIN = 4000`, `OTHER = 400`, `MAX_NAME = 80`. `clean_json` walks a JSON-like structure.
- `redact_profile(data)` walks `Profile.to_dict()`: every `password` becomes the boolean `has_password`, `product_key`
  becomes `has_product_key`, the free texts `comment`, `author` and `description` are renamed to `comment_text`,
  `author_text` and `description_text` and cleaned. `redact_differences(diffs)` renders the rows of `Profile.diff` and
  shows the product key as `<hidden>` on both sides.
- `redacted_copy(profile)`: a deep copy with every account password blanked and a custom product key replaced by the
  placeholder `XXXXX-XXXXX-XXXXX-XXXXX-XXXXX` (so the answer file stays well-formed where a key would be). The preview
  build is made from this copy, so `<Password><Value>`, `<ProductKey><Key>` and the `Extensions/Profile` JSON hold no
  secret by construction.
- `assert_redacted_build(result)` re-checks a build structurally: the XML is well-formed; every `Value` under a
  `Password` element is empty; every `Key` under `ProductKey` is empty, the placeholder or one of the generic edition
  keys of `render.EDITION_KEYS` (public values published by Microsoft, `public_keys()`); the embedded profile JSON
  parses and holds no password and no other key. A substring search for the secret values is not used: short or common
  passwords (`1`, `Admin`, `2026`) are substrings of ordinary content and would refuse exactly the starter profiles this
  toolkit produces. A failed check is a `RedactionError` (`redaction_failed`) and the text is never returned.
- `check_name(name)` accepts a profile or answer file name when, after NFC normalisation, it has 1 to 80 code points,
  every character satisfies `str.isalnum()` or is one of space, `_`, `.`, `-`, the first character is alphanumeric, the
  name ends with neither a space nor a dot, contains no `..` and no path separator, and its stem is not a reserved
  device name (`CON`, `PRN`, `AUX`, `NUL`, `COM1`-`COM9`, `LPT1`-`LPT9`, and whatever `os.path.isreserved` refuses for
  the name with `.json` or `.xml`: `COM0`, `LPT0`, the superscript variants). `str.isalnum()` accepts Cyrillic and every
  other script (the customer's profiles are Cyrillic) and refuses combining marks that did not fuse under NFC, format
  characters and controls. `safe_child(folder, name, suffix)` adds the refusal of `preset-*`, resolves the target and
  requires its parent to be the resolved folder, and refuses symlinks and reparse points on the folder and on the file.
- `profile_display(path, root)` (`mcp/workspace.py`): the profile file is reported as its path inside the program
  folder, or as the file name alone when it lies elsewhere, so the folder layout of the user's disk never leaves the
  machine; `list_profiles` gives names only.
- The journal never holds argument values beyond the whitelisted scalars (section 13); the log holds tool names and
  exception class names, never argument text.

## 13. Journal

`Journal` (`mcp/journal.py`) is a `deque(maxlen=1000)` behind a lock, memory only: nothing is written to disk, so
`test_portable.py` keeps its exact file list and no free text from a client can end up in a file the customer might
paste to an agent. `Entry(seq, time, transport, client, method, tool, args, ok, ms, note)`: `time` is `HH:MM:SS`,
`transport` is `stdio` or `http`, `client` is the name and version from `initialize` rendered by `render_client`
(letters, digits, space, `.`, `_`, `/`, `(`, `)`, `-`, at most 60 characters; anything else is `<client, N chars>`),
`tool` is the tool name or the resource URI rendered by `render_uri` (`<uri, N chars>` unless it is made of safe
characters), `args` is the rendering of `render_args`, `note` is the program's short note (`mode_required`,
`window_busy`, `window_timeout`, `exists`, `error -32601`, `internal`, `completed after timeout`, ...). `append` returns
the sequence number, `annotate(seq, note)` adds a note to an existing entry, `since(seq)` is what the monitor polls
every 250 ms, `count` and `last_time` feed the status bar.

`render_args(arguments, allowed)` renders only the keys the tool's schema declares (`allowed`); any other key, or a
key that is not an identifier, is `<unknown key, N chars>`. Booleans and integers are rendered as they are, strings as
they are only when the key is not one of `comment`, `author`, `name`, `query`, `value`, `title` and the value matches
`[A-Za-z0-9_.:-]{1,60}` (otherwise `<text, N chars>`), lists as `<list, N items>`, objects as `<object>`; at most 20
parts. Request and response bodies, headers and the token never enter the journal. `McpServer.handle` writes one entry
per handled message (notifications included) in the same way for both transports, and only after the entry exists does
it register the `completed after timeout` note of a pending write with that entry's sequence number.

## 14. Headless operation, the dispatcher and the command line

`winkickoff/__main__.py` is the entry of `python -m winkickoff` and of `WinKickOff.exe`. It parses the arguments with
`mcp.cli.parse_args` first; for `--mcp`, `--mcp-config` and `--version` it calls `run_headless` and returns its code
before `winkickoff.app` is imported, so a headless process never loads tkinter; only otherwise does it import
`winkickoff.app` and call `run(args, extras)`. A parser error with a headless flag on the command line (`is_headless`)
exits with the argparse code as a console program; without one it is shown in a message box through `app.fatal`.
`app.run()` without arguments (the console script entry of `pyproject.toml`) parses `sys.argv` itself and takes the
same headless branch.

`parse_args` uses `argparse` with `allow_abbrev=False` and `parse_known_args`: unknown extras (a file dropped onto a
shortcut, anything `Start-WinKickOff.cmd` forwards) are logged at INFO and ignored on the window path, and are an
error (exit 2) only with `--mcp` or `--mcp-config`. `--port` must pass `valid_port`, `--token` must match `TOKEN_RE`.

| Flag | Meaning |
|---|---|
| `--mcp stdio` | The headless stdio server: exit 0 on EOF, 2 on a start-up error, 3 without usable standard streams |
| `--mcp http` | The headless HTTP server on `127.0.0.1` (tests and a VM): runs `serve(httpd)` in the main thread until Ctrl+C; needs `--token` or `settings.mcp_token`; never writes settings |
| `--port N` | `0` or `1024` to `65535` for `--mcp http`; default `settings.mcp_port` |
| `--token TOKEN` | Overrides `settings.mcp_token` for this process only |
| `--mode read|edit|files` | The mode, default `read` |
| `--profile NAME_OR_PATH` | A preset id, a saved profile name in `profiles/`, or an absolute path (accepted here because the command line is written by the user into the client configuration, the trust level of the Open dialog); default `initial_profile()` |
| `--language CODE` | Applied once with `set_language` (the process is headless, so the global is safe); default `settings.language`, then Windows |
| `--mcp-config stdio|http` | Prints the `mcpServers` JSON of `client_config` and exits; honours `--port`, `--token`, `--mode` |
| `--version` | Prints `WinKickOff <APP_VERSION>` and exits |

`run_headless` for a server: `paths = app_paths()`, `setup_logging(paths, filename="mcp-<transport>-<pid>.log",
delay=True)`, `logging.captureWarnings(True)`, `housekeep_logs(paths.logs)` (removes `logs/mcp-*.log*` older than seven
days: housekeeping of the program's own files, not reachable through the protocol), then `prepare`: `Settings.load`
(never saved), `set_language`, `load_catalog` (a `CatalogError` is logged and exits 2, no `tk.Tk`), `with_imports`,
`Resources.load`, the profile from `--profile` or `initial_profile`, a `McpService` configured without a save callback,
`set_mode(args.mode)`, a `HeadlessWorkspace` behind an `InlineBridge`. `serve_stdio_process` opens the streams (exit 3
when there are none), builds the server with `transport="stdio"` and `has_window=False` and runs `serve_stdio`.
`serve_http_process` checks the token (exit 2 with "no access token: start the server once from the window or pass
--token"), binds (exit 2 when the port is taken), prints the URL and serves until Ctrl+C.

Log files: the window keeps `logs/winkickoff.log` exactly as before; every headless process logs into its own
`logs/mcp-stdio-<pid>.log` or `logs/mcp-http-<pid>.log`, opened lazily. Two processes never share a
`RotatingFileHandler` target: on Windows `doRollover` renames the file, the rename fails while another process holds it
open, and records would be lost. The file handler is the only handler, so `logging.lastResort` never writes to stderr
and stdout carries nothing but JSON lines. `cli.emit(text)` writes to `sys.stdout` when it exists; in a `--noconsole`
process without inherited handles it logs "no console: use python.exe or WinKickOff-mcp.exe for this flag" and the
process exits 3.

## 15. Client configuration and the second executable

`client_config(kind, paths, port, token, mode)` in `mcp/service.py` produces the `mcpServers` entry as JSON text; the
window copies it to the clipboard (`copy_mcp_config`, the HTTP kind only while the server runs, because with port `0`
the port is known only then) and `--mcp-config` prints it:

```json
{"mcpServers": {"winkickoff": {"type": "http", "url": "http://127.0.0.1:47831/mcp", "headers": {"Authorization": "Bearer <token>"}}}}
{"mcpServers": {"winkickoff": {"command": "C:\\...\\WinKickOff\\WinKickOff-mcp.exe", "args": ["--mode", "edit"]}}}
{"mcpServers": {"winkickoff": {"command": "C:\\...\\python.exe", "args": ["-m", "winkickoff", "--mcp", "stdio"], "env": {"PYTHONPATH": "C:\\...\\WinKickOff"}}}}
```

The stdio snippet names `WinKickOff-mcp.exe` next to `sys.executable` in the frozen build and, from sources,
`python.exe` (`pythonw.exe` is replaced) with `PYTHONPATH` set to the program root so the client may start from any
folder; `--mode edit` is appended when the window mode is `edit` or `files`, `--mode files` never. The URL always says
`127.0.0.1`: Node 17+ resolves `localhost` to `::1` first and this server listens on IPv4 only, so a `localhost` URL
fails or falls back slowly. Claude Code commands for the user page: `claude mcp add --transport http winkickoff
http://127.0.0.1:47831/mcp --header "Authorization: Bearer <token>"` and `claude mcp add winkickoff --
"<path>\WinKickOff-mcp.exe" --mode read`. Claude Desktop reads the stdio snippet from its configuration file (named in
the user page only; `test_sources.py` forbids such names in package sources) and cannot use the HTTP server, because its
custom connectors must be reachable from the internet; it therefore drives its own headless copy of the profile, not
the open window.

pi (the coding agent of earendil-works, 0.99.0 and later, MCP built in) reads the same HTTP entry from
`~/.pi/agent/mcp.json`; `pi-agent/` runs it in a Podman container with a local model (`pi-agent/README.md`). Its client
is its own implementation, not the SDK: it asks for 2025-11-25 and accepts our 2025-06-18, keeps `Mcp-Session-Id`,
opens no stream after the `405` to GET, sends `DELETE` on close, sends no `Origin` and builds `Host` from the URL, so
the container must reach the server through `127.0.0.1` (`--network=host`; on a Windows host only with WSL mirrored
networking). It runs the tool calls of one model message in parallel, a `codemode` script may start several calls
together, and it never retries a tool call, so more than `MAX_CONCURRENT` calls at once get `503`; it cuts a direct
result above 20 KB for the model. The CI job `pi-agent-container` builds that image (pi with its defaults: its own
tools, exposure `codemode`, its default prompt with the assistant's `AGENTS.md` as the context file; no project files;
the customer removed a wrapper that restricted pi on 02.10.2026) and has pi (1.0.0 since commit ef52d8e) connect to a
headless WinKickOff HTTP server on the runner (`.github/scripts/check_pi_agent.py`), with a stub model that records
the tools and the prompt pi sends and answers with a `codemode` script that calls WinKickOff tools; acceptance with
the window and a real model is pending. Through pi with direct exposure and llama.cpp the model sees only the text of
a tool error, which is why that text starts with the error kind (`ToolRegistry.call`: `"<kind>: <message>"`;
`result_too_large` likewise); a `codemode` script gets `isError` and `structuredContent` as well.

The Agent Skill `WinKickOff/skills/winkickoff` (`SKILL.md` and `references/`) teaches any of these clients how to use
the server: golden rules (read-only by default, the mode is the person's, no secrets, untrusted texts, one call at a
time), the tools by mode, every error kind with what to do, recipes and the domain. The portable build ships it next
to the exe, and the server serves it as resources (section 10); `tests/test_skill.py` fails when the skill names a
tool, an error kind, a rule, a group or a resource the server does not have, or misses one of the tools or error kinds.

The second executable: `WinKickOff.exe` is built with `--noconsole`, and in such a process `sys.stdin`, `sys.stdout`
and `sys.stderr` are `None` unless the parent passed pipes; a protocol channel must not depend on how a client spawns
the process. The portable build therefore adds the console executable `WinKickOff-mcp.exe`, built from
`winkickoff/mcp_main.py` next to `WinKickOff.exe` in the same one-folder build (CI only, never on the customer's PC);
both share `_internal\`, and `app_paths()` derives the root from `sys.executable`, so both share `settings.json`,
`profiles/`, `output/`, `logs/` and `admx/`. `cli.main()` prepends `--mcp stdio` unless a headless flag is present, so
`WinKickOff-mcp.exe --mode read` is a stdio server and `WinKickOff-mcp.exe --version` or `--mcp http` still work.
`WinKickOff.exe --mcp stdio` also works when the client passes pipes (`open_std_streams` falls back to the inherited
descriptors), but the documented command is the console executable.

## 16. Tests

All MCP tests use `unittest`, temporary folders from `tempfile.TemporaryDirectory()` and `AppPaths` built as in
`tests/test_ui_smoke.py` (the root in the temporary folder, `data=ROOT`, `docs_root=ROOT.parent`, so `data` and
`root` differ as in the frozen build). No test starts PowerShell, opens a visible window (windows are withdrawn or
moved off screen), writes outside its temporary folder or binds anything but `127.0.0.1` port `0`; `launch_elevated`
and `run_audit` are mocked on every window. Log assertions attach their own handler to the `winkickoff.mcp` logger and
never read the file of `setup_logging`, which returns early when a handler is already installed. The HTTP tests bind
loopback port `0` on every run, on the customer's PC too: a loopback bind raised no firewall dialog there (confirmed
30.09.2026), so no environment variable gates them.

The MCP test modules are `tests/test_mcp_*.py`: the JSON-RPC parsing, the schema checker and the `McpServer`
lifecycle in memory; every tool in every mode on the real catalog, including the no-secret test (a profile with a long
unique password and product key, every tool and resource called in `files` mode, neither string in any result, journal
entry or log record), the forbidden-functions test (the apply, audit, PowerShell, ADMX, settings, `os.startfile`,
`shutil.rmtree`, `Path.unlink` and `os.remove` entry points patched to fail while every tool and resource runs) and the
no-path test (no schema property whose name contains `path`); the resources and their refusals; the stdio loop with
`io.BytesIO` streams, the over-long line, and `-X importtime` subprocesses that prove `--version` and `--mcp stdio`
never import tkinter; the command line; the HTTP transport (every check of section 4, sessions, eviction, the
exclusive bind on win32, stop with an open socket, stop of a never-started thread); the window integration (a service
attached to a withdrawn `MainWindow`, requests from a helper thread while the test pumps `update()`, `window_busy`
under `_dialog` and under a grab, destroy and rebuild with the same service, the token surviving a window rebuild, the
monitor). `tests/test_mcp_settings.py` covers the three fields, `tests/test_sources.py` the rules of section 2 and
`tests/test_mcp_transports.py` (`CliHeadlessTest`) the file list of a headless stdio session (only
`mcp-stdio-<pid>.log`). Runner unchanged:
`python -m unittest discover -s tests -v` in `WinKickOff/`. CI runs the suite on windows-latest; the Linux job
`pi-agent-container` starts a headless server from the checkout for the pi image and runs no unit tests.
