# План: штатные возможности autounattend.xml, новое дерево каталога, панель параметров

Дата: 13.10.2026. Версия на момент плана: 1.4.0-rc.8, каталог 0.8. Запрос заказчика от 13.10.2026: предложить план
расширения по штатным функциям autounattend.xml; вести работу в отдельной ветке; встроенные разделы каталога перенести
в поддерево autounattend, штатные политики показывать отдельным деревом, остальное в «Прочее»; элементы управления
параметрами показывать над описанием; ограничить ширину и переносить строки для текстов импортированных каталогов.

Ветка: `unattend-tree` (создана от `main` после 1.4.0-rc.8). CI собирает только `main`, теги и pull request, поэтому в
ветке в `.github/workflows/build.yml` она добавлена в список веток; по окончании работы ветка вливается в `main`
обычным merge и список возвращается к прежнему.

## 1. Что генератор делает сейчас штатными средствами unattend

| Проход | Компонент | Что используется |
|---|---|---|
| windowsPE | Microsoft-Windows-Setup | RunSynchronous (обходы проверок TPM, Secure Boot, процессора, памяти, диска), UserData/ProductKey (ключ или запрос ключа и редакции) |
| windowsPE | Microsoft-Windows-International-Core-WinPE | язык установки и ввода |
| specialize | Microsoft-Windows-Deployment | RunSynchronous: Setup-System.ps1 (все правила этапов specialize и default-user), обход NRO |
| specialize | Microsoft-Windows-Shell-Setup | ComputerName (имя или шаблон), TimeZone |
| oobeSystem | Microsoft-Windows-Shell-Setup | OOBE (скрытие экранов, ProtectYourPC), UserAccounts/LocalAccounts или запрос учётной записи, FirstLogonCommands нет: задачи планировщика для Setup-User.ps1 и Post-OOBE.ps1 |
| oobeSystem | Microsoft-Windows-International-Core | язык интерфейса, локали, языки ввода |

Диск установщик спрашивает (DiskConfiguration нет), образ выбирается ключом редакции, драйверы не подключаются, всё
остальное (реестр, службы, функции, приложения) делают скрипты. Это осознанная схема: правила реестра работают и при
установке, и на работающей Windows («Этот ПК», возврат к умолчаниям), а штатная настройка unattend действует только при
установке и не читается обратно.

## 2. Штатные настройки unattend, которых нет: кандидаты

Оценка: польза для сценария заказчика (рабочие группы без домена, неспециалисты, постоянные атаки), риск, объём.
Каждый пункт проверяется по справочнику Unattended Windows Setup Reference и принимается в виртуальной машине на
образе 26200.

### 2.3. Общий механизм: действие «настройка unattend»

После решений заказчика штатные настройки XML нужны там, где реестр при установке не работает: Dynamic Update и
диагностика установки (пункт 4, проход windowsPE), рабочая группа (пункт 2) и раздел установки (пункт 9). Сейчас
правило может добавить только команду (`xml-pe-command`, `xml-specialize-command`) или экран OOBE (`xml-oobe`).
Предлагаю одно новое действие каталога `xml-setting`: проход, компонент, путь настройки (`DynamicUpdate/Enable`,
`Identification/JoinWorkgroup`), значение; генератор собирает настройки одного компонента и прохода в один элемент
`component` в порядке каталога. Нужны: проверка в `tools/Validate-Unattend.ps1` (новые компоненты, порядок,
`processorArchitecture`), чтение обратно в `core/actions_parser.py` (импорт собранного файла без встроенного профиля),
аудит: такие правила «нельзя проверить» (как сейчас правила установки), документация модели данных (раздел действий),
справочник (карточка на каждую настройку). Это одна задача на механизм, затем настройки добавляются как данные.
Конфликты между правилом реестра и штатной настройкой не разрешаются: по решению 5 для одной настройки существует
только один способ.

## 3. Новое дерево каталога

По решению 1 корни дерева делятся по механизму, а не по теме:

1. «autounattend.xml» (идентификатор `unattend`): формы данных (установка, учётные записи, языки) и правила, которые
   действуют штатными средствами файла ответов (действия `xml-*`): сейчас 11 правил групп «Установка» и «OOBE», плюс
   новые настройки раздела 2.
2. «Штатные политики» (`policies`): политики Windows из встроенного каталога, то есть правила, все действия которых
   пишут значения политик (ветки `Policies` реестра: сейчас 136 правил, среди них Defender, ASR, браузеры, Windows
   Update, телеметрия, Office, OneDrive), и все импортированные шаблоны (этой Windows, каталоги программы, папки и
   файлы каталогов), каждый импорт своей веткой. Корень неизвестных правил становится веткой этого корня и, как
   сейчас, не показывается, когда пуст.
3. «Прочее» (`other`): правила, которые ни штатные, ни политики: сейчас 123 правила (удаление приложений 34, значения
   реестра вне веток политик 69, службы, функции, скрипты, профиль по умолчанию, первый вход, после OOBE, папки «Этот
   ПК» и значки рабочего стола), а также 8 правил, у которых действия смешаны (политика и значение вне политик или
   скрипт: `update.unblock`, `uac.baseline`, `logging.audit-policy`, `privacy.telemetry-minimal`,
   `privacy.consumer-content`, `privacy.copilot-recall-off`, `apps.xbox-services-off`, `default-user.copilot-off`);
   их место решается по каждому правилу при реализации: правило с одним значением вне политик лучше разделить на два.

Тематические группы сохраняются под каждым корнем. Двенадцать групп содержат правила обоих механизмов (сеть,
печать, Windows Update, UAC, учётные записи, журналы, приложения, реклама, поиск, речь, драйверы, панель навигации):
такая группа остаётся под корнем, куда попадает большинство её правил, а остальные получают группу с тем же
заголовком под другим корнем (идентификатор с суффиксом, например `network.other`). Идентификаторы правил не
меняются, поэтому профили, диффы, пресеты и ссылки MCP остаются действительными; меняются идентификаторы части групп,
`groups.json` и переводы заголовков.

Механизм правила вычисляется из его действий (`catalog.mechanism(rule)`), и тест каталога требует, чтобы корень
группы совпадал с механизмом каждого её правила: новое правило попадает в нужный корень или проверка каталога
останавливает сборку. Корень импорта создаёт `admx.catalog_part`: ему достаточно получить родителя `policies`.
Что ещё затрагивается: счётчики и флажки групп (корень с тысячами политик), `make_rule_docs.py` (списки правил по
группам в документации), переводы `rules/lang/*.json`, навык `skills/winkickoff/references/concepts.md` (на пределе
20 КБ, придётся сокращать), `agents/AGENTS.md` и `pi-agent/AGENTS.md` (описание дерева), страницы документации «Окно»,
«ADMX», «MCP», тесты корней (`test_ui_smoke`, `test_admx`, `test_mcp_tools`, `test_catalog`).

## 5. Ширина и перенос строк для текстов импортированных каталогов

Длинные заголовки политик и вариантов из ADML не помещаются в окно. Меры по элементам:

- дерево: `Treeview` не переносит строки, поэтому заголовок обрезается до ширины колонки с многоточием, полный текст
  показывается в описании и во всплывающей подсказке при наведении; ширина колонки дерева следует ширине панели;
- подписи параметров: `wraplength` подписей привязан к ширине правой панели и пересчитывается при изменении размера
  окна (`<Configure>`);
- списки вариантов (Combobox): ширина поля ограничена шириной панели, вариант обрезается с многоточием, полный
  заголовок выбранного варианта показывается строкой под полем;
- окно сравнения и список сообщений: колонки с заголовками получают предел ширины и подсказку с полным текстом;
- описание уже переносит слова (`wrap=word`), не меняется.

Проверка: синтетические шаблоны тестов получают политику с заголовком и вариантами по 200 символов; тест окна
проверяет, что виджеты не шире панели.

## 7. Решения заказчика (13.10.2026)

1. «Штатные политики» содержат политики Windows из встроенного каталога и все импортированные политики; неизвестные
   правила остаются подразделом, невидимым, когда он пуст; «Прочее» получает то, что не попадает ни в политики, ни в
   штатные механизмы XML.
2. Разметка диска пока не нужна; нужна установка в указанный раздел. Разметка возможна отдельно после оценки.
3. Автовход только для учётных записей без пароля.
4. Папка драйверов на носителе: `\Drivers` рядом с autounattend.xml.
5. Штатная настройка XML добавляется только там, где реестр при установке не работает; очевидные конфликты между
   двумя способами не разрешаются: для одной настройки существует один способ.
