# План: штатные возможности autounattend.xml, новое дерево каталога, панель параметров

Дата: 13.10.2026. Версия на момент плана: 1.4.0-rc.8, каталог 0.8. Запрос заказчика от 13.10.2026: предложить план
расширения по штатным функциям autounattend.xml; вести работу в отдельной ветке; встроенные разделы каталога перенести
в поддерево autounattend, штатные политики показывать отдельным деревом, остальное в «Прочее»; элементы управления
параметрами показывать над описанием; ограничить ширину и переносить строки для текстов импортированных каталогов.

Ветка: `unattend-tree` (создана от `main` после 1.4.0-rc.8). CI собирает только `main`, теги и pull request, поэтому в
ветке в `.github/workflows/build.yml` она добавлена в список веток; по окончании работы ветка вливается в `main`
обычным merge и список возвращается к прежнему.

## 1. Что генератор делает сейчас штатными средствами unattend

| Проход | Компонент | Что используется |
|---|---|---|
| windowsPE | Microsoft-Windows-Setup | RunSynchronous (обходы проверок TPM, Secure Boot, процессора, памяти, диска), UserData/ProductKey (ключ или запрос ключа и редакции) |
| windowsPE | Microsoft-Windows-International-Core-WinPE | язык установки и ввода |
| specialize | Microsoft-Windows-Deployment | RunSynchronous: Setup-System.ps1 (все правила этапов specialize и default-user), обход NRO |
| specialize | Microsoft-Windows-Shell-Setup | ComputerName (имя или шаблон), TimeZone |
| oobeSystem | Microsoft-Windows-Shell-Setup | OOBE (скрытие экранов, ProtectYourPC), UserAccounts/LocalAccounts или запрос учётной записи, FirstLogonCommands нет: задачи планировщика для Setup-User.ps1 и Post-OOBE.ps1 |
| oobeSystem | Microsoft-Windows-International-Core | язык интерфейса, локали, языки ввода |

Диск установщик спрашивает (DiskConfiguration нет), образ выбирается ключом редакции, драйверы не подключаются, всё
остальное (реестр, службы, функции, приложения) делают скрипты. Это осознанная схема: правила реестра работают и при
установке, и на работающей Windows («Этот ПК», возврат к умолчаниям), а штатная настройка unattend действует только при
установке и не читается обратно.

## 2. Штатные настройки unattend, которых нет: кандидаты

Оценка: польза для сценария заказчика (рабочие группы без домена, неспециалисты, постоянные атаки), риск, объём.
Каждый пункт проверяется по справочнику Unattended Windows Setup Reference и принимается в виртуальной машине на
образе 26200.

### 2.1. Рекомендую сделать

| № | Настройка | Зачем | Как в WinKickOff | Риск и заметки |
|---|---|---|---|---|
| 1 | Microsoft-Windows-Security-SPP, SkipAutoActivation | Двенадцать редакций устанавливаются ключами KMS и без хоста KMS не активируются: без этой настройки Windows раз за разом пытается активироваться и показывает ошибки | Правило `install.skip-auto-activation` (specialize), по умолчанию включено, когда редакция не Pro и не Education | Малый. ### 2.2. Возможны позже или не нужны

| Настройка | Решение |
|---|---|
| ImageInstall/InstallFrom (индекс или имя образа) | Редакцию уже выбирает ключ; нужно только для образов без ei.cfg с одной редакцией. Отложить |
| TerminalServices (fDenyTSConnections, UserAuthentication, SecurityLayer), Networking-MPSSVC-Svc (профили брандмауэра, группы правил), LUA-Settings/EnableLUA, ErrorReportingCore/DisableWER | Те же значения уже пишут правила реестра групп «Удалённый доступ», «Сеть», «UAC», «Телеметрия»; штатные настройки действуют только при установке. | TCPIP и DNS-Client (статические адреса, DNS-суффиксы) | В рабочих группах заказчика адреса выдаёт DHCP; статика индивидуальна для ПК. Отложить; при необходимости сделать по образцу шаблона имени компьютера |
| Themes, VisualEffects, TaskbarLinks, StartTiles, Display, OEM-логотип | Косметика, вне приоритетов проекта |
| FolderLocations/ProfilesDirectory (профили на другом диске) | Microsoft не поддерживает такую систему при обновлении. Не делать |
| CopyProfile | Профиль по умолчанию уже настраивают правила этапа default-user. Не делать |
| SystemRestore/DisableSR, TPM-Tasks/ClearTpm, WinRE/UninstallWindowsRE, Deployment/Reseal, PnpSysprep | Снижают защиту или относятся к sysprep и аудиту. Не делать |
| OOBE/NetworkLocation, SkipMachineOOBE, SkipUserOOBE, WindowsFeatures, IE-InternetExplorer | Устарели или не действуют в Windows 11. Не делать |
| FirstLogonCommands вместо задач планировщика | Задачи выбраны осознанно: выполняются для каждого пользователя и на батарее. Оставить |
| UserAccounts/AdministratorPassword | Встроенный администратор остаётся отключённым по правилу. Не делать |

### 2.3. Общий механизм: действие «настройка unattend»

Пункты 1, 3, 4, 8, 9 требуют писать произвольные настройки компонентов в XML. Сейчас правило может добавить только
команду (`xml-pe-command`, `xml-specialize-command`) или экран OOBE (`xml-oobe`). Предлагаю одно новое действие
каталога `xml-setting`: проход, компонент, путь настройки (`OOBE/HideEULAPage`, `DiskConfiguration/...`), значение;
генератор собирает настройки одного компонента и прохода в один элемент `component` в порядке каталога. Нужны:
проверка в `tools/Validate-Unattend.ps1` (новые компоненты, порядок, `processorArchitecture`), чтение обратно в
`core/actions_parser.py` (импорт собранного файла без встроенного профиля), аудит: такие правила «нельзя проверить» (как
сейчас правила установки), документация модели данных (раздел действий), справочник (карточка на каждую настройку).
Это одна задача на механизм, затем правила добавляются как данные.

## 3. Новое дерево каталога

Сейчас у дерева 16 корней встроенного каталога, по корню на каждый импорт шаблонов и корень «Неизвестные правила и
политики». Предлагаю три корня:

1. «autounattend.xml» (идентификатор группы `unattend`): все 16 встроенных корней становятся его ветками. Идентификаторы
   групп и правил не меняются, поэтому профили, диффы, ссылки MCP (`show_item`, `list_rules`) и документация правил
   остаются действительными; меняются только `parent` в `groups.json` и переводы заголовка.
2. «Штатные политики» (`policies`): импорты шаблонов этой Windows (вид `system`) и каталоги программы (`bundled`). Это
   политики, которые Windows поставляет сама, в отличие от правил WinKickOff.
3. «Прочее» (`other`): импорты из папок и файлов каталогов (виды `folder`, `package`) и корень неизвестных правил.
   Если заказчик предпочитает, импорты всех видов могут жить во втором корне, а в «Прочее» останутся только
   неизвестные правила: решить при согласовании.

Корень импорта создаёт `admx.catalog_part`: ему достаточно получить родителя по виду импорта. Что ещё затрагивается:
счётчики и флажки групп (корень с тысячами политик), `make_rule_docs.py` (списки правил по группам в документации),
переводы `rules/lang/*.json`, навык `skills/winkickoff/references/concepts.md` (на пределе 20 КБ, придётся сокращать),
`agents/AGENTS.md` и `pi-agent/AGENTS.md` (описание дерева), страницы документации «Окно», «ADMX», «MCP», тесты
корней (`test_ui_smoke`, `test_admx`, `test_mcp_tools`). Профили и MCP не меняются.

Вариант с отдельными вкладками (три виджета дерева) возможен позже: он дороже (поиск, Назад и Вперёд, выбор узла из
MCP и из сообщений работают с одним деревом) и не даёт ничего, кроме внешнего вида.

## 4. Правая панель: параметры сверху, описание ниже

Сейчас в правой панели описание, под ним кнопки группы и параметры. Меняется порядок упаковки в `window_detail`:
сверху блок параметров правила (или кнопки группы: «Включить все», «Выключить все», «Сбросить», для импорта
«Переименовать», «Показать»), ниже описание, которое занимает остаток высоты и прокручивается. Блок параметров
ограничен по высоте примерно третью панели и получает прокрутку, когда параметров много (импортированные политики с
десятком элементов). Формы данных (установка, учётные записи, языки) не меняются.

## 5. Ширина и перенос строк для текстов импортированных каталогов

Длинные заголовки политик и вариантов из ADML не помещаются в окно. Меры по элементам:

- дерево: `Treeview` не переносит строки, поэтому заголовок обрезается до ширины колонки с многоточием, полный текст
  показывается в описании и во всплывающей подсказке при наведении; ширина колонки дерева следует ширине панели;
- подписи параметров: `wraplength` подписей привязан к ширине правой панели и пересчитывается при изменении размера
  окна (`<Configure>`);
- списки вариантов (Combobox): ширина поля ограничена шириной панели, вариант обрезается с многоточием, полный
  заголовок выбранного варианта показывается строкой под полем;
- окно сравнения и список сообщений: колонки с заголовками получают предел ширины и подсказку с полным текстом;
- описание уже переносит слова (`wrap=word`), не меняется.

Проверка: синтетические шаблоны тестов получают политику с заголовком и вариантами по 200 символов; тест окна
проверяет, что виджеты не шире панели.

## 6. Порядок работ и оценка

| Этап | Задача | Объём | Приёмка |
|---|---|---|---|
| 1 | Правая панель (раздел 4) | день | окно: тесты и просмотр |
| 2 | Ширина и перенос (раздел 5) | день | окно: тесты с длинными заголовками |
| 3 | Новое дерево (раздел 3) | два-три дня | тесты, документация, навык; профили без изменений |
| 4 | Механизм `xml-setting` (раздел 2.3) с первыми правилами: SkipAutoActivation, PreventDeviceEncryption, Dynamic Update и диагностика установки | три дня | валидатор, импорт собранного файла, ВМ |
| 5 | Рабочая группа, сведения о поддержке (пункты 2, 7) | день | ВМ, «Этот ПК» для правил реестра |
| 6 | Драйверы с носителя (пункт 5) | два дня | ВМ с папкой драйверов |
| 7 | Автовход (пункт 8) | день | ВМ |
| 8 | Разметка диска (пункт 9) | два-три дня | ВМ, несколько прогонов: чистый диск, диск с данными, второй диск |

Каждый этап заканчивается коммитом в ветке с зелёным CI; версия поднимается до 1.5.0-rc.N при вливании в `main`,
поскольку меняются каталог (новые группы и действие), шаблоны среды выполнения и формат профиля (поля диска, рабочей
группы, автовхода).

## 7. Вопросы заказчику

1. Что входит в «Штатные политики»: только шаблоны этой Windows и каталоги программы, или все импорты, включая папки
   и файлы каталогов (тогда «Прочее» содержит только неизвестные правила)?
2. Разметка диска: нужен ли режим «очистить диск 0» в принципе, учитывая риск потери данных, или достаточно режима
   «установить в указанный раздел»?
3. Автовход: допустим ли пароль в файле ответов в виде Base64 (так хранит сам Windows Setup), или автовход нужен
   только для учётных записей без пароля?
4. Папка драйверов на носителе: подходит ли имя `\Drivers` рядом с autounattend.xml?
5. Там, где есть и правило реестра, и штатная настройка (BitLocker, UAC, брандмауэр, RDP), оставить реестр как
   основной способ, а штатную настройку добавлять только там, где реестр не работает при установке?
